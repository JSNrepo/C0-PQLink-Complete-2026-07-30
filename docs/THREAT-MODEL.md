# Threat model

## Security objective

C0-PQLink attempts to establish an authenticated live session between a
provisioned constrained client and a key-owning peer, then protect short
bidirectional application records against passive capture and active network
tampering.

It specifically addresses the live-connection use case. It does not verify
boot code, firmware images, updates, or digital signatures.

## Protected assets

- confidentiality and integrity of application plaintext;
- the ML-KEM shared secret and derived traffic/chain keys;
- the per-device PSK;
- peer private-key material;
- freshness and direction of records inside an established session;
- the configured migration policy, epoch, key slot, and key ID.

## Adversary in scope

The network attacker may:

- observe and retain all frames for future analysis;
- inject, modify, replay, reorder, delay, duplicate, fragment, or drop frames;
- send unauthenticated handshakes to consume bandwidth or computation;
- know the protocol, source code, public key, key ID, device ID, and epoch;
- later obtain a cryptographically relevant quantum computer.

The tests exercise loss, forged fragments, forged Finished messages, forged
records, replay, and torn journal writes. Tests are evidence of specific
behaviors, not a proof that no protocol attack exists.

## Assumptions

1. Every device receives an independent uniformly random 32-byte PSK. A fleet
   default PSK is prohibited.
2. The client pins the correct canonical ML-KEM-512 public key, 16-byte key ID,
   and epoch through a trusted provisioning path.
3. The peer protects its ML-KEM private key or key-generation seed.
4. Both 16-byte handshake nonces and the ML-KEM randomness come from a
   cryptographically secure source with adequate backtracking and
   prediction resistance for the platform.
5. Ascon nonces never repeat with the same traffic key. C0-PQLink enforces
   monotonic in-session sequence numbers; the application must establish a
   fresh session after reboot rather than restoring a live key/sequence pair.
6. Secret erasure is effective on the target compiler and hardware.
7. The application treats every nonzero return as failure and does not use
   unauthenticated plaintext.
8. The transport consumes a sent frame before returning, because the client
   may reuse that buffer for the reply.

## Intended properties

### Post-quantum session confidentiality

The recorded handshake contains an ML-KEM-512 ciphertext generated by the
device. Assuming FIPS 203 ML-KEM-512 remains secure, later quantum
cryptanalysis should not reveal the ML-KEM shared secret. The key schedule
also mixes the provisioned PSK.

This is not a claim of everlasting security: endpoint compromise, weak
entropy, protocol flaws, implementation leakage, or future cryptanalysis can
invalidate it.

### Provisioned peer and device authentication

The PSK authenticates Hello, Challenge, ciphertext fragments, and ACKs.
Bilateral Finished then proves that both sides derived keys from the same PSK,
ML-KEM shared secret, and transcript.

C0-PQLink does not implement certificates, public-key signatures, anonymous
internet discovery, or a general PKI. Authentication is only as scalable and
secure as per-device PSK provisioning and protection.

### Handshake transcript integrity

Finished binds the authenticated Hello and Challenge cores plus all 768 exact
ciphertext bytes. Changing the negotiated suite, epoch, key ID, either nonce,
or ciphertext causes Finished verification to fail.

### Record confidentiality, integrity, direction, and replay control

Ascon-AEAD128 protects application ciphertext with the frame header and
sequence as associated data. Directional keys/nonces and the direction flag
separate client and peer traffic. Only the exact next sequence is accepted.

### Transactional ratchet

In ratchet mode, receive state advances only after a valid tag. An attacker
cannot desynchronize the chain simply by injecting an invalid record. Erased
past chain states should make earlier message keys harder to recover from a
later chain-state compromise.

The ratchet does not provide post-compromise healing, asynchronous skipped-key
handling, endpoint authentication beyond the PSK, or fresh PQ entropy after
the handshake.

### Downgrade-resistant local policy

The migration helper accepts only nondecreasing policy states and epochs and
authenticates each A/B journal record. A torn inactive-slot write leaves the
previous valid record recoverable.

If an attacker can roll back the entire nonvolatile medium to an older valid
image, software alone cannot detect that. Use a monotonic hardware counter,
secure element, trusted time, or peer-enforced minimum epoch.

## Explicitly out of scope

- malicious or compromised application code;
- extraction of PSKs or live secrets through physical access;
- invasive attacks, debug-port abuse, cold boot, DMA, or memory remanence;
- timing, cache, power, electromagnetic, acoustic, or fault attacks;
- denial of service and radio jamming;
- traffic-analysis resistance, padding, cover traffic, or metadata privacy;
- peer availability, distributed consensus, or multi-peer roaming;
- group messaging, broadcast authentication, or multicast;
- secure boot, firmware update, attestation, or signature verification;
- certification, FIPS validation, CAVP validation, Common Criteria, or
  regulatory approval.

## Denial-of-service boundary

The authenticated preflight makes an unauthenticated sender fail before
ML-KEM begins on the client. It does not eliminate:

- repeated valid requests from a compromised PSK holder;
- radio receive/parse cost;
- state exhaustion at the peer;
- packet-loss amplification from hostile jamming;
- deliberate reconnects that repeatedly trigger ML-KEM.

Peers should rate-limit by device identity and source, bound concurrent
sessions, expire incomplete ciphertext assemblies, and avoid detailed error
oracles. The 32-bit session ID is only a demultiplexing hint: a production
peer should also scope sessions to the authenticated device and transport
association, and reject active collisions.

## Side-channel status

The C core avoids secret-dependent branches in its explicit signed
multiplication correction. On AVR with hardware `MUL`, it requests four
fixed-latency unsigned 8×8 products for each 16×16 product. Host functional
and sanitizer tests pass.

That is not a complete constant-time claim. A release claim requires linked
target disassembly, whole-call control-flow inspection, compiler-version
pinning, timing analysis, and preferably power/EM testing. The included AVR
audit script is a gate, but no AVR toolchain result is bundled in v0.1.0.

## Security review status

No independent cryptographic audit has been completed. Treat all protocol
properties above as design goals supported by tests, not as a formal proof or
certification.
